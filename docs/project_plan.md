# 프로젝트 계획: 최종 발표까지 누가 무엇을 하나

제안서 발표(11/7) 이후 최종 발표(12/12 또는 12/19)까지의 역할 분담과 일정입니다. 코드(수집부터 보고서까지)는 이미 만들어져 있어서, **남은 일은 실제로 돌리고, 검증하고, 해석하고, 발표하는 것**입니다.
조원 수(5~6명)와 각자의 일정에 맞게 담당자 칸을 채우고, 필요하면 역할을 합치거나 나누세요.

실라버스는 예비 초안이라 바뀔 수 있습니다. KLMS 공지를 확인하세요.

## 2. 역할 (조원 5~6명 기준)

한 사람이 한 역할의 **주 담당**이고, 다른 역할을 돕는 **보조**를 둡니다. 5명이면 4번과 5번을 합치고, 6명이면 그대로 씁니다.
담당자 칸은 직접 채우세요.

| # | 역할 | 주 담당 | 보조 | 하는 일 | 주로 보는 코드 |
|---|---|---|---|---|---|
| 1 | **팀장·일정·발표 총괄** | | | 일정 관리, PR 병합, 교수님·조교 문의, 발표 자료 통합, 리허설 진행 | `docs/`, `CONTRIBUTING.md` |
| 2 | **데이터 수집** | | | YouTube API 키 발급, 전체 기간 영상·자막 수집, 결측 점검, 팀 드라이브에 CSV 공유 | `collect/` |
| 3 | **종목 매칭·전처리** | | | 종목 사전과 별칭 점검, 오탐 줄이기, 월별 언급 종목 수 보고, 게스트 영상 구분 확인 | `text/clean.py`, `text/mentions.py` |
| 4 | **톤 점수화(LLM·사전)** | | | LLM 프롬프트와 모델 설정, 채점 실행, 사전 점수와 비교, 사전 보강 | `text/tone.py`, `text/lexicon_ko.py` |
| 5 | **라벨링·타당성 검증** | | | 라벨 표본 100문장 생성, 2명 이상이 라벨링하도록 조율, 일치도(kappa) 계산, 척도 수정 | `analysis/validation.py` |
| 6 | **수익률 분석·해석** | | | 분석 실행, 강건성 점검, 검정력, 결과 표·그림, 판정 규칙대로 해석 | `analysis/`, `report.py` |

**모든 조원 공통**: 라벨링 20문장(역할 5가 배정), 발표 자료 리허설 참석, 최종 발표 질의응답 대비(자기 역할 부분을 설명할 수 있어야 함).
실라버스상 AI 도구는 쓸 수 있지만 **제출하는 코드는 본인이 설명하고 수정·재현할 수 있어야** 합니다.

## 3. 단계별 일정과 산출물

### 단계 0: 제안서 발표 (11/6~11/7)
- [ ] 역할 담당자 정하기(위 표 채우기)
- [ ] 교수님·조교에게 확인: 1개 아이디어로 발표해도 되는지, 제안서에서 어떤 점을 보는지
- [ ] 모든 조원이 저장소를 받아서 `pytest`와 `python -m jeoningu demo`가 되는지 확인(`CONTRIBUTING.md` 1절)
- [ ] 팀 드라이브 폴더 만들기(스크립트 CSV, 결과 공유용)
- [ ] 피드백을 받아 적기

### 단계 1: 파일럿과 설정 확정 (11/8~11/14)
- [ ] (2) 소량 수집 시험: `collect --max-videos 30`, 이어서 1년치로 시험해 차단이 생기는지 확인
- [ ] (3) 파일럿 1년치로 **월별 언급 종목 수** 세기
- [ ] (4) LLM 공급자와 모델 정하고 `config.toml`의 `tone.llm_model` 채우기, 문장 20개로 시험 채점
- [ ] (5) 라벨링 척도 정의서 한 장(−2~+2, 전망/설명 구분 기준)
- [ ] (1) 제안서 피드백 정리해서 설계 반영 여부 결정
- **게이트 G1 (11/14)**: 월별로 두 그룹 모두 3종목 이상인 달이 파일럿 기준 60개월 환산 미만이면 **H2(시장 수준)를 주 분석**으로 바꾼다(`docs/design.md`의 기준). 결정은 팀 회의에서 기록으로 남긴다.

### 단계 2: 전체 수집과 라벨링 (11/15~11/21, 중간고사 2 주간)
- [ ] (2) **전체 기간(2018-09~2025-12) 수집** 완료, 자막 성공률과 실패 사유 보고
- [ ] (3) 전체 데이터로 `preprocess`, `mentions` 실행, 종목 매칭 오탐 점검(무작위 200행 확인)
- [ ] (5) `label-sample --n 100` 생성, 조원별 20문장씩 배정(각 문장을 서로 다른 2명이 라벨링)
- 중간고사 주간이라 작업량이 많지 않게, 수집은 시작만 하고 돌려 두면 되는 것부터 배치
- **게이트 G2 (11/21)**: 전체 데이터가 드라이브에 올라가 있고 모든 조원이 같은 파일로 작업한다.

### 단계 3: 점수화, 검증, 분석 (11/22~12/5)
- [ ] (4) `tone --method llm` 전체 실행(캐시 덕분에 중단해도 이어짐), 비용과 실패율 기록
- [ ] (5) 라벨링 결과 취합, `validate`로 일치도 확인
- **게이트 G3 (11/28 전후)**: 라벨러 간 일치도가 낮으면(일반적으로 kappa 0.6 미만이면 낮다고 봄, 팀이 기준 확정) **모델 탓을 하기 전에 척도 정의부터 고치고** 다시 라벨링
- [ ] (6) `analyze` 실행: H1, H2, 사전 추세 점검, 검정력, 강건성(톤 임계값 변경, 게스트 포함 시, 사전 vs LLM)
- [ ] (6) 결과 해석: **사전에 정한 판정 규칙대로**(`analysis/decision.py`). 결과를 본 뒤 규칙을 바꾸지 않는다
- [ ] (4) 12/5 수업(LLM·API 활용)에서 배운 점을 프롬프트와 평가에 반영할지 검토

- **게이트 G4 (12/5)**: **결과 동결.** 이후에는 설정과 코드를 바꾸지 않고 발표 준비만 한다. 바꾸려면 팀장 승인과 이유 기록.

## 4. 결정해야 할 것 (미정)

| 항목 | 현재 기본값 | 누가, 언제까지 |
|---|---|---|
| 주 분석을 H1(종목)로 갈지 H2(시장)로 갈지 | H1 주, H2 병행 | 역할 3·6, G1(11/14) |
| LLM 공급자와 모델 | 비어 있음 | 역할 4, 11/14 |
| "의미 있는 크기"(`meaningful_alpha`) | 월 2% | 팀 전체, 결과를 보기 **전**에 확정 |
| 라벨러 간 일치도 기준 | 확정 필요(참고: kappa 0.6) | 역할 5, G3 |
| 게스트 영상 처리 | 제외 | 역할 3, 11/14 |
| 최종 발표 날짜 | 12/12 또는 12/19 | 역할 1, KLMS 확인 |

## 5. 위험과 대응

| 위험 | 대응 |
|---|---|
| 대량 자막 수집이 차단됨 | 수집기는 이어받기를 지원한다. 대기 시간을 늘리고 시간대를 나눠 재실행. 한 사람 PC에서 하지 않고 나눠 수집할 수 있음 |
| 월별 언급 종목이 너무 적음 | G1에서 H2를 주 분석으로 전환 |
| 라벨러 간 일치도가 낮음 | 척도 정의서와 예시를 고쳐서 재라벨링 |
| LLM 호출 비용·실패 | 같은 문장은 캐시되어 재요청하지 않음. 먼저 소량으로 비용을 추정 |
| 중간고사·Case 4와 겹침 | 11/21과 11/28 주에는 팀 작업을 가볍게 잡았음 |
| 일정 지연 | 12/5 결과 동결, 12/10 최종본 확정은 움직이지 않는 것으로 하고 나머지를 조정 |
| 결과가 기대와 다름 | 판정 규칙을 미리 정해 둔 이유. 유의하지 않은 결과도 보고 가능 |

## 6. 소통과 작업 방식

- **정기 회의**: 주 1회(수업 후 토요일이 가장 쉬움), 30분. 안건은 지난 주 산출물, 이번 주 목표, 막힌 것, 게이트 확인.
- **작업 추적**: GitHub Issues에 역할별 할 일을 올리고, 작업은 브랜치에서 하고 Pull Request로 합친다(`CONTRIBUTING.md` 4절).
- **결과 공유**: `outputs/`는 git에 올라가지 않으므로 `report.md`와 그림은 드라이브에 올리거나 PR에 첨부한다. 어떤 설정으로 돌렸는지 같이 적는다.
- **데이터**: 스크립트와 수업 데이터는 저장소에 올리지 않는다(저작권, 라이선스). 비밀값도 올리지 않는다.
